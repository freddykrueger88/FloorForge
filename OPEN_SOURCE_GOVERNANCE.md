# OPEN_SOURCE_GOVERNANCE.md

# OpenFloorball Coach Platform

## Open-Source-Governance und Projektorganisation

---

# 1. Ziel

OpenFloorball soll langfristig als offenes Projekt bestehen.

Das bedeutet:

* offener Code
* transparente Entscheidungen
* gemeinschaftliche Entwicklung
* nachhaltige Pflege

---

# 2. Grundprinzipien

Das Projekt basiert auf:

* Offenheit
* Respekt
* Transparenz
* technischer Qualität
* gemeinsamer Verantwortung

---

# 3. Projektwerte

OpenFloorball steht für:

* Wissen teilen
* Vereine stärken
* Nachwuchs fördern
* digitale Selbstbestimmung

---

# 4. Keine Abhängigkeit von Einzelpersonen

Das Projekt darf nicht abhängig sein von:

* einer Person
* einem Verein
* einem Unternehmen

---

# 5. Projektstruktur

Empfohlen:

```text id="8m3q7k"

Community

↓

Contributor

↓

Maintainer

↓

Core Team

```

---

# 6. Community

Community-Mitglieder können:

* Ideen einbringen
* Fehler melden
* Dokumentation verbessern
* Inhalte teilen

---

# 7. Contributor

Contributor leisten aktive Beiträge.

Beispiele:

* Code
* Übersetzungen
* Designs
* Tests
* Floorball-Wissen

---

# 8. Maintainer

Maintainer verantworten:

* Qualität
* Reviews
* Releases
* technische Richtung

---

# 9. Core Team

Das Core Team entscheidet über:

* Architektur
* langfristige Strategie
* wichtige Änderungen

---

# 10. Entscheidungsprinzip

Entscheidungen sollen sein:

* nachvollziehbar
* dokumentiert
* offen diskutierbar

---

# 11. Technische Entscheidungen

Größere Entscheidungen benötigen:

Dokument:

```text id="4q8n2m"

Problem

↓

Optionen

↓

Bewertung

↓

Entscheidung

```

---

# 12. Feature-Anfragen

Neue Ideen werden bewertet nach:

* Nutzen
* Aufwand
* Datenschutz
* Wartbarkeit

---

# 13. Keine Feature-Überladung

Nicht jede Idee wird umgesetzt.

Frage:

Verbessert es wirklich Training oder Vereinsarbeit?

---

# 14. Beiträge

Jeder Beitrag sollte:

* verständlich sein
* getestet sein
* dokumentiert sein

---

# 15. Pull Requests

Ein Pull Request benötigt:

* Beschreibung
* Begründung
* Tests
* mögliche Auswirkungen

---

# 16. Code Review

Prüfung:

* Funktion
* Sicherheit
* Datenschutz
* Architektur
* Wartbarkeit

---

# 17. Branch-Strategie

Beispiel:

```text id="7p5m9v"

main

↓

development

↓

feature branches

```

---

# 18. Dokumentationspflicht

Neue Funktionen benötigen:

* technische Dokumentation
* Nutzerbeschreibung
* gegebenenfalls Beispiele

---

# 19. Lizenzmodell

Die Software benötigt eine klare Lizenz.

Ziele:

* freie Nutzung ermöglichen
* Beiträge schützen
* Offenheit erhalten

---

# 20. Inhalte und Code trennen

Wichtig:

Softwarelizenz ≠ Inhaltslizenz.

---

Beispiele:

Code:

Open-Source-Lizenz

---

Taktiken:

separate Inhaltslizenz

---

# 21. Community-Regeln

Alle Beteiligten verpflichten sich zu:

* respektvoller Kommunikation
* konstruktiver Kritik
* fairer Zusammenarbeit

---

# 22. Code of Conduct

Nicht akzeptiert:

* persönliche Angriffe
* Diskriminierung
* Belästigung
* Missbrauch der Plattform

---

# 23. Datenschutz in der Community

Offene Entwicklung bedeutet nicht:

offene persönliche Daten.

---

Schutz:

* keine privaten Nutzerdaten im Repository
* keine echten Spielerinformationen in Tests

---

# 24. Sicherheit melden

Sicherheitsprobleme nicht öffentlich veröffentlichen.

Ablauf:

```text id="3n6q8m"

Meldung

↓

Prüfung

↓

Behebung

↓

Veröffentlichung

```

---

# 25. Roadmap-Entwicklung

Die Community kann mitgestalten.

Aber:

Strategie bleibt nachvollziehbar.

---

# 26. Finanzierung

Mögliche Modelle:

* Spenden
* Förderungen
* Vereinsunterstützung
* Hosting-Angebote
* Supportleistungen

---

Nicht:

* Verkauf persönlicher Daten
* verstecktes Tracking

---

# 27. Community-Wissen

Floorball-Fachwissen ist wertvoll.

Daher:

* Autoren sichtbar machen
* Quellen respektieren
* Lizenzen beachten

---

# 28. Nachhaltigkeit

Langfristige Ziele:

* stabile Releases
* aktive Community
* gute Dokumentation
* einfache Mitarbeit

---

# 29. Claude-Code-Regeln

Bei Projektentscheidungen prüfen:

1. Unterstützt es Offenheit?
2. Ist es langfristig wartbar?
3. Gibt es eine Community-Perspektive?
4. Werden Nutzerrechte respektiert?
5. Vermeidet es Abhängigkeiten?

---

# 30. Leitgedanke

Open Source bedeutet nicht nur, Code sichtbar zu machen.

Open Source bedeutet, gemeinsam Verantwortung zu übernehmen.
